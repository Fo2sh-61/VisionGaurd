# What these models are

`MODELS.md` is generated by `engine/tools/audit_models.py` and lists what each file
*contains*. This file is hand-written and says what each file is *for*, and what it is
not. Read this one first.

None of it was documented when the folder was handed over — everything below was
recovered by reading the checkpoints.

---

## The headline: the weapons model is prompted, not trained

`yolov8m-worldv2-school.pt` (343 MB, saved 2026-05-06) is the weapons detector. It is a
stock **YOLO-World v2** open-vocabulary model with 18 text prompts baked in:

> knife · kitchen knife · pocket knife · box cutter · utility knife · razor blade ·
> screwdriver · scissors · hammer · axe · baseball bat · handgun · pistol · rifle ·
> shotgun · machete · sword · dagger

**This matters.** No weights were fine-tuned — the 343 MB is the CLIP text encoder plus
the saved embeddings for those 18 phrases. It is zero-shot: it has never seen a school
corridor, an Egyptian classroom, or a 4CIF ceiling-mounted camera.

Consequences for planning:

- **Good:** it works today, with no training and no labelled data. Weapons can be wired
  into the pipeline immediately.
- **Bad:** its accuracy on real footage is completely unknown, and open-vocab detectors
  are typically weaker than a fine-tuned closed-set detector on a narrow domain.
- **The prompt list is a product decision, not a technical one.** `screwdriver`,
  `scissors` and `hammer` are in there. Every school has scissors in every classroom and
  a screwdriver in every maintenance cupboard. Expect a very high false-alarm rate on
  those three specifically — which the mandatory human-review gate absorbs, but only up
  to the point where reviewers stop trusting it.
- The improvement path is one of: tune the prompt list, raise per-class thresholds, or
  collect real footage and fine-tune a closed-set detector. The eval harness has to exist
  before we can tell which of those actually helped.

**Cross-check available for free:** `yolov8n-oiv7.pt` is a 6.9 MB Open Images V7 detector
whose 601 classes already include `Handgun`, `Rifle`, `Shotgun`, `Knife`, `Kitchen knife`,
`Dagger`, `Sword`, `Axe`, `Hammer`, `Screwdriver`, `Scissors` and a generic `Weapon`. It's
a genuinely trained closed-set model. Worth scoring both against the same golden clips —
it may beat the prompted model, and it's 50× smaller.

## The second custom model: appearance search

`yolov8m-worldv2-search.pt` (343 MB, saved 2026-05-09), 35 prompts:

> person · t-shirt · shirt · jacket · coat · hoodie · sweater · vest · dress · pants ·
> shorts · skirt · shoes · boots · sandals · cap · hat · helmet · hijab · glasses ·
> sunglasses · mask · scarf · belt · tie · backpack · handbag · suitcase · umbrella ·
> phone · bottle · book · laptop · cup · sports ball

This serves two features at once:

- **Lost items** — `backpack`, `handbag`, `suitcase`, `umbrella`, `phone`, `bottle`,
  `book`, `laptop`, `cup` map directly onto the item dropdown on the Lost Items page.
  Colour comes from a separate histogram step, not from the model.
- **Track a person** — the clothing prompts describe what someone is wearing, which is
  the appearance half of re-identification.

`hijab` in the list is a good sign: whoever built it was thinking about the actual student
population, not a Western benchmark set.

## Everything else

| File | What it is | Use |
|---|---|---|
| `yolov8s.pt` | Stock COCO YOLOv8s, 80 classes, 11.2M params, 500 epochs | **The workhorse.** Person detection for intrusion, counting, tracking |
| `yolo11m.pt` | Stock COCO YOLO11m, 80 classes | Bigger/slower alternative to the above |
| `yolov8s-pose.pt` | COCO pose, 1 class + 17 keypoints, 11.6M params | **Fight detection foundation.** Pose-over-time is far cheaper than a video classifier and doesn't need the deferred fights model to get started |
| `yolov8n-oiv7.pt` | Open Images V7, 601 classes, 3.5M params | Weapons cross-check; broad object vocabulary for lost items |
| `yolov8m-worldv2.pt` | Stock YOLO-World v2, un-prompted (COCO 80) | The base the two custom variants were made from. Re-prompt it for new open-vocab tasks |
| `face_detection_yunet_2023mar.onnx` | OpenCV Zoo YuNet, 227 KB | Face **detection** for attendance. Runs via `cv2.FaceDetectorYN`, no extra dependency |
| `face_recognition_sface_2021dec.onnx` | OpenCV Zoo SFace, 37 MB | Face **embedding** for attendance. Runs via `cv2.FaceRecognizerSF` |
| `osnet_x1_0_market1501.pth` | OSNet body re-ID, 512-d embedding, classifier head (751, 512) | Body appearance matching for track-a-person |

### Two traps in that table

**Which OSNet variant is unresolved.** The classifier shape `(751, 512)` confirms stock
Market-1501 weights for **`osnet_x1_0`**. But `osnet_ain_x1_0` is a *different
architecture* that `torchreid` downloads separately, and the two are not interchangeable
— load one and score against the other and you get confident nonsense, not an error.

The re-ID model that will actually ship is being handed over separately. **Do not wire
track-a-person against the file in this folder on the assumption it is the right one.**
Confirm the architecture first. See `DEV_PLAN.md` §1.4 — this is also what blocks the
choice of Python version, because `torchreid` may not support the newest interpreter.

**Face recognition is SFace, and that is settled.** See `DEV_PLAN.md` §0.2. The
alternative sometimes suggested is InsightFace ArcFace R50 (`w600k_r50.onnx`, 166 MB),
which is a stronger model — but it is **not** in use here and switching to it is not
planned. Embeddings from two face models are not comparable, so a switch means
re-enrolling every face in the school. `gallery.py` refuses to mix them, by design.

## The `.engine` files: do not archive these

Five TensorRT engines are present. All were exported by **ultralytics 8.4.46**, FP16,
batch 1, static shapes, in May 2026, on this laptop's RTX 2080.

```
yolov8m-worldv2-school-960.engine   960×960
yolov8m-worldv2-search-960.engine   960×960
yolov8s-480.engine                  480×480
yolov8s-pose-640.engine             640×640
yolov8n-oiv7.engine
```

A TensorRT plan is compiled against one GPU architecture and one TensorRT version.
**None of these will load on the RTX 6000 Ada workstation.** They are also built by a
*newer* ultralytics (8.4.46) than the one currently installed here (8.4.7), so they may
not load reliably on this machine either.

The rule: **`.pt` is the artifact, `.engine` is a build output.** Engines get rebuilt
from the `.pt` on whatever machine will run them, as a deployment step. Never treat one
as the thing you keep.

## Regenerating the inventory

```
python engine/tools/audit_models.py
```

Writes `MODELS.md` plus one `<name>.yaml` sidecar per weight file. The script never
imports model code and never installs anything — unimportable classes are stubbed during
unpickling, because loading a YOLO-World checkpoint will otherwise try to
`pip install git+.../CLIP.git` mid-audit.
